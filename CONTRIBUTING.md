## Согласование и SDD

- Небольшое изменение оформляется задачей с ID требования, ожидаемым результатом и способом проверки. Сложное изменение или фича получает спецификацию с критериями приёмки до реализации.
- Архитектурное решение, меняющее принятые границы, оформляется ADR по [шаблону](docs/adr-template.md). Илья утверждает технические ADR; Accepted обязателен. При замене принятого ADR предыдущий получает Superseded одновременно с принятием нового. Обратная связь Карины и руководства клуба по текущим ADR ожидается.
- При конфликте PRD и Accepted ADR сообщить владельцу решения. Изменение продуктовых требований согласовать с Кариной и внести в PRD до реализации.
- Использовать ID требований в задачах, спецификациях и PR. При изменении поведения актуализировать соответствующие спецификации и проверки.

## Планирование и делегирование

- Планировать недельными спринтами с учётом частичной занятости, сессии и праздников. Уточнить доступность каждого участника (Q-4 из PRD 1.2).
- Декомпозировать работы текущего релиза до задач размера не больше M. Список задач и оценки вести в [GitHub Projects](https://github.com/orgs/Sreda-Media/projects/1) по мере приближения релиза.
- Если работа заблокирована, исполнитель отмечает в карточке, что мешает продолжить, от кого нужен ответ или действие и какую часть задачи можно выполнить независимо. Если продолжить нечего, задачу можно поставить на паузу.
- Если взятый объём превышает доступное время, исполнитель сообщает об этом в карточке. На ближайшей синхронизации команда пересматривает объём с учётом доступности участников. При нехватке ресурсов сначала откладывают Could, затем Should. Если требуется изменить Must, Илья согласует изменение с Кариной и обновляет PRD.
- При делегировании определить владельца, ожидаемый результат, границы полномочий, зависимости и критерии приёмки. Владелец выбирает способ реализации, готовит документацию и предоставляет результат для ревью. Межкомпонентные задачи согласовывать с владельцами затронутых областей.

## Локальная проверка

Одна команда для чистого checkout:

```bash
test -f apps/cms-api/.env || cp apps/cms-api/.env.example apps/cms-api/.env
just verify
```

Перед `just verify` запусти тестовый PostgreSQL 18 с параметрами из `apps/cms-api/.env`. Шаблон рассчитан на `127.0.0.1:5432`, базу и пользователя `sreda`. При другом адресе или учётных данных обнови локальный `.env`. Пользователю БД нужно право создавать тестовую базу Django.

`verify` проверяет документацию (включая `docs-build` — MkDocs `--strict` без публикации), конфигурацию, workflows, историю на секреты, пример CMS-лога, provisioning алертов, конфигурацию Uptime Kuma, хостовые шаблоны Caddy/Docker/journald (`check-host-config`), SLO, дашборд и выключенные правила (`check-slo`), команды в bash-блоках документации (`check-runbook`), SHA-пины внешних GitHub Actions (`audit-workflows`), CMS Web и витрину. Также в `verify` входят конфигурационные проверки `check-env-contract`, `check-ports`, `check-image-pins` и операционная политика `check-ops-policy`. Рецепт `api-check` запускает полный gate CMS API: Ruff, Pyright, Django checks, проверку миграций, `deploy-strict` и pytest. Строгая deploy-проверка использует синтетический `.env.deploy-check`. Для отдельного запуска доступны `just api-check`, `just check-logs`, `just check-alerts`, `just check-uptime`, `just check-host-config`, `just check-slo`, `just check-runbook`, `just audit-workflows`, `just docs-build`, `just link-check`, `just audit-hardening`, `just check-alert-runbooks`, `just check-env-contract`, `just check-ports`, `just check-image-pins` и `just check-ops-policy`.

Остальные рецепты намеренно не входят в `verify`: `just coverage`/`just cov` (неблокирующий сбор отчётов), `just pre-commit` (локальный предпрогон без установки хуков), `just alert-drill` (проверка алертов плюс тестовая запись в Loki, если он поднят), `just obs-health` (только чтение HTTP/состояния контура), `just logs-profile-check` (read-only сверка compose-профилей метрик и датасорса Grafana, сервисы не запускаются), `just backup-drill` (DRY_RUN резервного копирования), `just sign-artifact dist`, `just release-manifest dist` (манифест артефакта как код: не подписывает и не выкладывает артефакт) и `just verify-artifact dist` (хэш и опциональная cosign-подпись), `just api-db-up`/`just api-db-down` (локальный PostgreSQL 18), `just docs-serve` и `just bootstrap`. Также вне `verify`: `just doctor` (справка по инструментам, всегда exit 0), `just dr-drill` (DR-репетиция во временном каталоге) и `just check-github-policy` (read-only чтение защиты `main`). Эти три рецепта ничего не включают и не меняют GitHub: `doctor` только печатает справку, `dr-drill` работает локально во временном каталоге, `check-github-policy` только читает настройки репозитория. Ещё три рецепта намеренно не входят в `verify` и CI: `just release-readiness` (таблица готовности с вердиктом `READY`/`NO-GO`), `just check-commits` (subject, тело и `Refs:` новых коммитов) и `just check-issues` (read-only отчёт о карточках без label/assignee и stale). Они тоже read-only и ничего не включают: только читают репозиторий и GitHub, готовят отчёт и не меняют ни флаги, ни настройки, ни карточки. Выкладка готовится в `deploy.yml`, но не выполняется без `ENABLE_DEPLOY=true` и явного `dry_run=false`; smoke после выкладки — `just smoke <url>` с необязательным `SREDA_SMOKE_MARKER`.

Зависимости для чистого checkout: Python 3.14+, [uv](https://docs.astral.sh/uv/) 0.9+, Node.js 22+, pnpm 12.x (через `corepack`), Go 1.24+ (для gitleaks и actionlint) и `just`. Если `just` не установлен, используй `uvx --from rust-just just verify`. На Windows запускай команды через Git Bash: рецепты рассчитаны на bash.

Проверки сайта (`build-site`) подключаются по мере появления `apps/site`; сейчас это открытая зависимость PR #16. Те же проверки выполняются в CI, а итоговый обязательный статус называется `ci` — он будет зелёным только если все применимые проверки прошли.

### Контракт логирования

Логи — это часть зоны ответственности DevOps, но контракт затрагивает и компоненты. Согласно [ADR 0005](docs/adr/0005-observability-glitchtip.md), приложение пишет **JSON в stdout**, а инфраструктура забирает логи на стороне хоста. Клиенты Kafka, прямую отправку логов в брокер или в браузерный SDK добавлять нельзя: бэкенд соблюдает контракт событий (`event`, `component`, `operation`, `outcome`, `timestamp`, `environment`, `release`), фронтенд отправляет только исключения в GlitchTip и просмотры в Umami.

Локально контракт проверяется командой `just check-logs` (скрипт [check_log_schema.py](scripts/check_log_schema.py)); она входит в `just verify`. Пример корректной строки — [valid.jsonl](docs/examples/logs/valid.jsonl). Подготовленный стек Grafana/Loki/Alloy/Prometheus/PostgreSQL/GlitchTip лежит в `deploy/observability/`. Grafana/Loki/Alloy работают по умолчанию; Prometheus, node_exporter и blackbox_exporter поднимаются только с `--profile logs` и только после ресурсного gate ADR 0006 §4. Внешняя проба `sreda-external` хранится в шаблоне с `${SREDA_SITE_URL}` и не добавляется в активный `prometheus.yml` до появления тестового адреса. Согласованность профилей и датасорса проверяет `just logs-profile-check` без запуска сервисов.

## Git и GitHub

Команда использует trunk-based development. Единственная постоянная ветка — `main`. После каждого слияния проект должен собираться и сохранять уже доступное пользователю поведение. Публичный выпуск планируется отдельно.

1. Создай короткоживущую ветку от актуальной `main`. Один PR решает одну проверяемую задачу. Большую фичу разбей на части, каждую из которых можно собрать, проверить и влить отдельно. Размер оценивай по объёму ревью и времени до интеграции.
2. Укажи в PR задачу, затронутые ID требований, ожидаемое поведение, способ проверки и зоны ответственности. Приложи результат теста или ссылку на preview. При изменении ожидаемого результата теста укажи требование или исправляемую ошибку и объясни, почему новое ожидание корректно.

### Ревью и слияние PR

Все изменения в `main` проходят через Pull Request с обязательными автоматическими проверками. Прямой push в `main` запрещён.

#### Обычные участники

- Каждый PR требует как минимум одного независимого одобрения.
- Ревьюер сверяет результат с критериями приёмки и проверяет, что тесты способны обнаружить нарушение нужного поведения. Для исправления дефекта по возможности показать один тест до и после исправления.
- При изменении зоны ответственности другого участника необходимо согласование с её владельцем.
- После последнего содержательного изменения требуется актуальное одобрение.

#### Ответственный maintainer

Ответственный maintainer, назначенный в разделе «Команда и ответственность», вправе объединять собственные PR без обязательного независимого одобрения при соблюдении всех условий:

1. Изменение находится в пределах его зоны ответственности.
2. Изменение не затрагивает контракты, полномочия, обязанности или технические решения, принадлежащие другим участникам.
3. Все обязательные автоматические проверки завершились успешно на актуальной версии изменений.
4. Выполнена самостоятельная проверка изменений и критериев приёмки; блокирующие замечания и обсуждения закрыты.
5. В PR указаны затронутые зоны ответственности, полученные согласования и основание для self-merge.

Если изменение затрагивает зону ответственности другого участника, получить его явное согласование через актуальное независимое одобрение до слияния. Согласование распространяется на изменённые файлы, межкомпонентные контракты, инфраструктурные зависимости и обязанности участников. Изменение правил распределения полномочий согласовывается с затронутыми участниками до слияния.

Право self-merge привязано к назначенному maintainer. Другие администраторы, разработчики и ИИ-агенты не получают его автоматически.

#### Использование bypass

Maintainer может применять bypass только для требования независимого одобрения собственного PR в пределах описанных условий. Основание фиксируется в описании PR. GitHub не определяет семантические границы ответственности автоматически; проверка применимости исключения — ответственность maintainer.

Если после слияния обязательная проверка сломалась, автор с ревьюером (если он участвовал) приоритетно исправляет или отменяет изменение через PR.

Bypass сохраняет обязательный PR, обязательные проверки CI, актуальность ветки перед слиянием, разрешение обсуждений, запреты force push и удаления `main`. ИИ-агенты не получают отдельных прав bypass. За подготовленные агентом изменения отвечает автор PR.

### Настройка защиты main

Защита `main` реализуется двумя независимыми активными GitHub Rulesets:

1. **`main-core-protection`:** обязательный PR (0 approvals в этом наборе), обязательный статус `ci`, актуальность ветки перед слиянием, разрешение всех обсуждений, запрет force push и удаления ветки. Список bypass пуст.
2. **`main-review-policy`:** обязательный PR, одно независимое одобрение, сброс устаревших одобрений и одобрение последнего reviewable push. Bypass только для персонального аккаунта назначенного maintainer (`@Cewerty`) в режиме For pull requests only.

Оба набора применяются к `main`. CODEOWNERS сохраняет назначение владельцев для ревью; глобальное обязательное одобрение CODEOWNERS пока не включается. При CI по путям итоговый статус должен завершаться на каждом PR и учитывать все затронутые компоненты. Оба rulesets активированы 24.11.2026, классическое правило удалено после проверки полного покрытия. Настройки меняет ответственный maintainer; DevOps отвечает за сохранение работоспособности обязательного `ci`.

### Поэтапный выпуск

Когда фича требует нескольких PR, сначала интегрируй самостоятельно проверяемые части. Если новый пользовательский сценарий нужно включить позже, используй временный release flag. В PR укажи исходное состояние, владельца и условие удаления. Проверь прежний сценарий при выключенном флаге и новый при включённом. Способ выкладки и возврата предыдущей рабочей сборки описывает Костян в `docs/DEPLOYMENT.md`.

## Ревью и завершение задачи

- Ревью выполняет владелец затронутой области или другой назначенный участник. Для React запрашивать периодическое экспертное ревью Кирилла; частота уточняется (Q-2 из PRD 1.2). Код DHR используется как образец; замечания системного характера фиксируются в локальных соглашениях и чек-листах. При существенных проблемах оценить рефакторинг или регенерацию модуля после уточнения спецификации и проверок. Запасной вариант при невозможности обеспечить качество React — htmx по отдельному архитектурному решению.
- При изменениях дизайна Полина и Саня проверяют применимость макетов и соответствие реализации.
- При изменениях инфраструктуры проверку инструкций может выполнить другой участник с нужными доступами.
- Для релиза 0.1 команда проверяет условия выпуска, Must-требования и применимые NFR по [PRD, §6–8](docs/prd.md). В задаче выпуска собирают результаты проверок и подтверждение Карины, что ссылку можно давать в пабликах. Критерии закрытия витрины приведены во [фронтенд-эпике](https://github.com/Sreda-Media/sreda-media/issues/10).

### Definition of Done

Автор и ревьюер используют этот список при проверке PR. Задача завершена после слияния.

- [ ] **Поведение.** Выполнен каждый критерий приёмки из задачи или спецификации. В PR указан способ проверки и результат. Тесты нового или изменённого поведения дополнены там, где существующие проверки пропустили бы регрессию.
- [ ] **Quality gate.** На актуальной версии PR успешно завершились обязательные проверки для затронутых компонентов, включая применимые тесты, линтеры, проверку типов и сборку. Изменение ожидаемого результата теста обосновано согласно разделу «Git и GitHub».
- [ ] **Интеграции.** Если затронут контракт между компонентами или поведение зависит от окружения, соответствующий сценарий проверен в тестовом окружении или preview. Результат зафиксирован в PR.
- [ ] **Контракты и документация.** Соблюдены доменные инварианты и принятые ADR. При изменении контракта или границы автор PR лично проверил обоснование и последствия для потребителей. Изменение согласовано по правилам SDD, затронутые спецификации и документация актуализированы.
- [ ] **Ревью и слияние.** Получено независимое одобрение либо выполнены все условия разрешённого self-merge. Согласования владельцев затронутых областей получены, блокирующие замечания закрыты, PR объединён с `main`.
