# Design: DevOps hardening — After address

- **Статус:** одобрено пользователем 25.11.2026, реализация не начиналась.
- **Ветка:** `observability/foundation`.
- **Автор:** Костян (Zisvit), DevOps.
- **Смежный документ:** `2026-11-25-devops-hardening-ready-now-design.md`.

## 1. Контекст

Часть DevOps-работы имеет смысл только после появления объекта наблюдения:
сайта в `main` (PR #16) и тестового адреса (Q-1 с Артёмом). Этот спек
фиксирует границу между подготовкой и включением. Ничего из описанного здесь
не должно включаться в обязательный статус `ci` до явного решения.

## 2. Внешние условия и гейты

| Условие | Что становится возможным |
| --- | --- |
| Слияние PR #16 в `main` | Реальная сборка `apps/site`, smoke и Lighthouse |
| Q-1: домен, DNS, тестовый адрес | Uptime Kuma мониторы, synthetic-проверки, реальный smoke |
| `ENABLE_DEPLOY=true`, `dry_run=false` | Атомарная выкладка из `deploy.yml` |
| `ENABLE_DOCS_PAGES=true` | Публикация MkDocs |
| `ENABLE_PROVENANCE=true` | Keyless-подпись и SLSA-attestations в CI |
| Решение Ильи по ADR 0006 | Выбор хостинга и независимой точки проверки |

## 3. Цели и границы

Цели: подготовить вторую точку проверки, provenance артефакта и порядок
включения SLO-алертов; явно зафиксировать, что включение — отдельное решение.

Вне границ: выбор провайдера, покупка домена, изменение `ruleset`, работа с
`serv`, изменение чужих PR и файлов `apps/site`.

## 4. Компоненты

### 4.1 Synthesis: вторая точка проверки

- `scripts/synthetic-check.sh` — проверка главной (200), несуществующей
  страницы (404) и маркера контента по `SREDA_SITE_URL`. Переиспользует
  `scripts/smoke-static.sh`, не дублирует логику.
- Дополнительные панели Grafana на базе `slo.json` из первого спека и
  метрик Uptime Kuma.
- Внешний вызов мониторинга подключается через переменные окружения и
  остаётся выключенным до Q-1.

ПОТОК ДАННЫХ: `SREDA_SITE_URL` → `synthetic-check.sh` → метрика/лог → Loki →
дашборд и (после включения) contact point.

### 4.2 Provenance артефакта

- В `supply-chain.yml` — загрузка SBOM как артефакта через `upload-artifact`;
  это безопасно и может попасть в репозиторий вместе со Spec 1.
- Отдельный gated workflow: keyless `cosign sign-blob` и SLSA provenance
  attestation для `dist/artifact.tar.gz`. Guard `ENABLE_PROVENANCE=true` и
  `workflow_dispatch`; в обязательный статус `ci` не входит.
- `scripts/verify-artifact.sh` остаётся точкой проверки: сначала `sha256sum -c`,
  затем опционально `cosign verify-blob`.

### 4.3 Включение SLO-алертов

Новые правила burn-rate из Spec 1 остаются `enabled="false"`. Включение —
отдельный коммит после PR #16 и Q-1: заменить флаг, задать контакты Telegram
через env, проверить `just check-alerts` и зафиксировать дату в
`docs/DEVOPS-STATUS.md`. Уведомления о несуществующем сайте не отправляются.

## 5. Обработка ошибок и безопасность

- При отсутствии `SREDA_SITE_URL` synthetic-скрипт завершается с сообщением
  «проверка не настроена» и кодом 0: это подготовка, а не инцидент.
- При недоступности сайта после включения — ненулевой код и запись в лог;
  уведомление идёт только в настроенный contact point.
- Provenance workflow не имеет write-доступа к репозиторию: только
  `contents: read` и `id-token: write` для keyless-подписи.
- Никаких секретов в репозитории; PAT в `kilo.jsonc` — зона владельца.

## 6. Тестирование

До включения: `bash -n`, `py_compile`, `actionlint`, `zizmor`,
`scripts/check.py`, `scripts/config_lint.py`, `mkdocs build --strict`;
synthetic-скрипт проверяется на локальном `python -m http.server` с теми же
ожиданиями 200/404/маркер, что и `smoke-static.sh`.

После появления адреса: ручной `workflow_dispatch` с `dry_run=true`, сверка
хэша и подписи, затем только по решению пользователя — реальный smoke и
включение алертов.

## 7. Критерии приёмки

Spec 2 считается подготовленным, когда скрипты и workflow лежат в ветке,
все гейты выставлены в выключенное состояние, проверки зелёные, а переход в
рабочее состояние описан одной таблицей гейтов. Реальная выкладка, публикация
Pages и уведомления до выполнения условий не выполняются.
