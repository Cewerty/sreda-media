# Подготовить CI и проверяемую выкладку статической витрины

Владелец — Костя. Этап 0.0, первый потребитель — сайт 0.1. На неделю 23–29 ноября планируется первый рабочий PR. Следующий результат эпика — проверка выкладки и отката на тестовом адресе.

## Результат

Саня может открыть PR с изменением материала, воспроизвести проверку локально и по результату CI понять, можно ли слить изменение. Для демо команда может развернуть проверенный статический артефакт и вернуть предыдущий. Основание — ADR 0001, 0006–0008, 0014–0015 и Definition of Done в CONTRIBUTING.md.

## Подзадачи

1. **Включить начальную защиту main.** Администратор включает обязательный PR и независимое ревью, запрещает прямой push, force push и удаление ветки. Временное исключение касается только ещё не существующего обязательного статуса.
2. **Собрать проверку для сайта.** Выбрать из таблицы ниже подходящие части и указать в PR итоговый выбор. Документировать одну команду для чистого checkout; использовать её в CI. Изменение материала или медиа запускает валидацию и сборку. Фронтенд предоставляет минимальный собираемый Astro-сайт с одним материалом. CMS, PostgreSQL и DNS для этого шага не требуются.
3. **Сделать статус обязательным.** Приложить красный запуск на некорректном материале, зелёный после исправления и завершившийся статус PR только с документацией. Проверить, что обязательная ошибка блокирует merge. После демонстрации администратор включает проверенный статус в защите main. В ADR 0007 приведены примеры поведения; способ реализации выбирает Костя.
4. **Проверить выкладку статического артефакта.** На тестовом адресе опубликовать две различимые сборки, проверить главную и 404, показать сохранение рабочей версии при ошибке выкладки и возврат к предыдущей. Записать команды в runbook. Q-1 с Артёмом нужен для финальной выкладки на домен. 
5. **Исследовать и настроить Vercel Preview Deployments.** Костя проверяет пригодность Vercel для ревью PR и оценивает вариант размещения публичной витрины. Задачу можно исследовать параллельно с подготовкой CI. Настройка preview зависит от появления собираемого Astro-сайта.

### Подзадача 5. Vercel Preview Deployments

**Результат.** Полина и Саня могут открыть сборку конкретного PR на компьютере и телефоне для взаимного ревью. Илья получает обоснованную рекомендацию о применимости Vercel для preview и production.

**Контекст.** ADR 0007, 0015, NFR-AVAIL-01, NFR-COST-01, ADR 0006 (текущая схема VPS/Caddy). Для исследования использовать тестовый адрес, пока открыт Q-1 по DNS.

**Критерии приёмки**

- [ ] Проверены условия тарифов Vercel для командного проекта, включая GitHub-интеграцию, доступ участников, лимиты и стоимость в рамках общего бюджета.
- [ ] Если тариф и доступность позволяют, настроен preview для PR из монорепозитория с воспроизводимой сборкой Astro. Новый commit обновляет preview, ссылка доступна Полине и Сане. Проверена изоляция preview от production и отсутствие production-секретов в preview.
- [ ] Проверена доступность тестового адреса из российских домашних и мобильных сетей. При наличии собственного тестового домена отдельно проверена его доступность. Если домен ещё недоступен, проверка отмечена как открытая зависимость. Одна успешная проверка не гарантирует доступность через всех провайдеров.
- [ ] Проверено, что preview согласуется с обязательным Quality Gate в GitHub Actions. Ошибочный PR не может привести к публичному выпуску в обход CI.
- [ ] Подготовлено краткое сравнение Vercel и VPS/Caddy для витрины по стоимости, доступности, rollback, сложности эксплуатации, интеграции с будущей CMS и совместимости с agreed same-origin схемой. Костя рекомендует один вариант для preview и один для production и прикладывает результаты пробного развёртывания либо подтверждённые причины, по которым оно невозможно.

**Как проверить.** Приложить ссылки на актуальную документацию Vercel, PR и preview (если доступен), результаты сетевых проверок и короткое обоснование выбора. Решение об изменении production-хостинга принимает Илья через ADR 0006. При отрицательном результате исследование считается завершённым после обоснования и выбора доступного способа preview на VPS. Подключение Vercel не является условием закрытия CI или MVP.

## Граница эпика

Фундамент для v1 означает, что к CI можно подключить следующего потребителя общего контракта. Реальные CMS jobs появятся вместе с кодом CMS. Выбор фонового транспорта остаётся в ADR 0013. Финальная продуктовая приёмка на домене и подтверждение Карины отслеживаются в задаче выпуска.
