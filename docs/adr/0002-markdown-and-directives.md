# ADR 0002: Формат статей — Markdown + фиксированный набор директив, а не MDX

## Дата: 20-11-2026

## Статус: Accepted

Принято владельцем проекта 22-11-2026.

## Контекст

Статьи пишут участники медийки, в том числе новички. Глава медийки готова обучить авторов Markdown, но не программированию.

По итогам опроса (20-11-2026):

- в статьях нужны **все** виды вставок: длинный текст разбавляют блоками, и это важная часть подачи;
- в статье обычно 1–5 картинок, максимум около 10 (например, подборки вроде «котик-программист по дням недели»);
- у каждой статьи есть обложка (от дизайнера или сгенерированная);
- расшифровки подкастов публикуются вместе с видео или аудио эпизода;
- видео живёт на внешних площадках (VK, Rutube, YouTube), на сайт его не загружают;
- кода немного: небольшие фрагменты, большие примеры дробятся на части, а крупные разборы идут на стримах.

Изначально рассматривался Astro + MDX. Но MDX — это не Markdown: знак `<` или фигурные скобки `{}` в обычном тексте ломают сборку, а сообщение об ошибке новичку ничего не объясняет.

Кроме того, превью в микро-CMS (react-markdown) и рендер на сайте (Astro) должны выглядеть одинаково (ADR 0008).

## Решение

Принято решение использовать **обычный Markdown (`.md`) для статей и фиксированный набор вставок на синтаксисе generic directives (remark-directive)**, потому что этот синтаксис:

- остаётся валидным Markdown, и спецсимволы в тексте его не ломают;
- обрабатывается одними и теми же remark-плагинами в Astro и в react-markdown, поэтому превью в CMS совпадает с сайтом;
- набор вставок закрытый и короткий, его можно целиком описать в памятке на одну страницу.

MDX остаётся исключением для редких сложных материалов, которые собирают разработчики.

### Детали реализации

1. **Набор вставок для MVP:**

   | Директива | Что делает |
   | --- | --- |
   | `::figure{src="..." caption="..."}` | Картинка с подписью и альт-текстом |
   | `::video{src="..."}` | Видео из VK, Rutube или YouTube (определяется по ссылке) |
   | `::audio{src="..."}` | Аудиоплеер, например эпизод подкаста |
   | `:::note` / `:::warning` | Врезки |
   | `:::spoiler[Заголовок]` | Рендерится в нативный `<details>` |

2. **Позже:**
   - `:::gallery` — галерея на 5–10 картинок; до неё подборки делаются серией `::figure`;
   - опросы — только ссылкой на опрос в Telegram или VK. Свой опрос требует серверного состояния и противоречит ADR 0001.
3. Обложка задаётся полем `cover` во frontmatter, а не директивой.
4. Код — стандартные блоки с указанием языка, подсветка через Expressive Code.
5. remark-плагины, которые превращают директивы в компоненты, лежат в общем пакете `packages/remark-directives` (ADR 0007) и подключаются и в Astro, и в микро-CMS.
6. Неизвестная директива или директива без обязательных атрибутов считается ошибкой сборки, а не тихо игнорируется.
7. Набор расширяется только через PR, в котором одновременно обновляются плагин, компонент и памятка для авторов.
8. Памятка для авторов: базовый Markdown, frontmatter, список директив с примерами.

```markdown
---
title: Как я начал программировать
cover: ./cover.png
rubric: opyt
authors: [ivanov]
---

Обычный текст, в котором можно писать x < y и {скобки}.

::figure{src="./setup.png" caption="Рабочее место автора"}

::video{src="https://rutube.ru/video/..."}

:::spoiler[Ответ]
Спрятанный текст
:::
```

## Альтернативы

* **MDX для всех статей:**
  * *Плюсы:* в тексте можно использовать любые компоненты, максимальная гибкость.
  * *Минусы:* ломается на `<` и `{}`, непонятные ошибки, по сути программирование. Новичкам не подходит. Превью в CMS сложно сделать безопасным и совпадающим с сайтом.

* **Markdoc:**
  * *Плюсы:* создан для контента с компонентами, безопаснее MDX.
  * *Минусы:* отдельный синтаксис тегов `{% %}`, хуже поддержка в экосистеме react-markdown/remark, авторам пришлось бы учить ещё один диалект.

* **Только чистый Markdown без вставок (HTML вставляют руками):**
  * *Плюсы:* ничего не нужно настраивать.
  * *Минусы:* авторы копипастят iframe, вёрстка ломается, нет единого вида, есть риск XSS. Глава медийки прямо хочет разбавлять текст блоками.

## Последствия

### Положительные

* [+] Порог входа для авторов — только Markdown и пять директив.
* [+] Превью в микро-CMS совпадает с сайтом.
* [+] Единый вид вставок, их можно централизованно менять.

### Отрицательные

* [-] Набор директив нужно поддерживать в двух местах сборки (общий пакет снижает риск).
* [-] Новая вставка требует работы разработчика.
* [-] Памятку для авторов нужно держать в актуальном состоянии.
