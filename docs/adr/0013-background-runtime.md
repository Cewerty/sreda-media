# ADR 0013: Фоновые задачи в PostgreSQL с отдельными scheduler и worker без Redis

## Дата: 21-11-2026

## Статус: Proposed

## Контекст

Перед 0.2 Илья и Костя сравнят PostgreSQL-вариант ниже и TaskIQ с RabbitMQ на одном напоминании. Проверят повторную доставку, падение до и после внешнего эффекта, восстановление после простоя и эксплуатацию в бюджете VPS. Выбор транспорта и топологии остаётся открытым. Требования к эффектам заданы в принятом ADR 0012.

Напоминания и сводки (0.2), RSS-автопостинг (0.3), scheduled articles, экспорт и сборки (0.4) должны переживать рестарт CMS/бота. Периодический цикл внутри web или aiogram polling дублирует работу при нескольких процессах и теряет in-memory schedule. PyBot решает это через TaskIQ + Redis, но Redis исключён PRD §10, бюджет инфраструктуры ограничен ~500 ₽/месяц.

PostgreSQL уже выбран для CMS (ADR 0004). При текущей частоте контента полноценный брокер и универсальный task framework не обязательны, но «cron вызовет функцию» недостаточно без durable state, дедупликации, восстановления и явных часов.

Основания: NOTIF-01–04, PUB-03, EDIT-08/12, NFR-OPS-02/03, NFR-COST-01. Семантика попыток определяется ADR 0012, не этим runtime.

## Решение

Предлагается использовать **PostgreSQL как источник расписаний и состояния задач, отдельные Django management commands для scheduler и worker**, без Redis. Сначала — по одному экземпляру каждого. Это ограниченный механизм для известных операций, не собственный аналог Celery.

### Детали реализации

#### 1. Разделение обязанностей

- `scheduler` периодически находит due deadlines, scheduled articles и даты запуска регулярных операций, создаёт durable намерения с unique key. Он не вызывает Telegram/VK/GitHub внутри бизнес-транзакции.
- `worker` резервирует доступные записи, вызывает фиксированный обработчик операции и сохраняет результат по ADR 0012.
- `cms-api` обслуживает HTTP; `bot` обрабатывает входящие Telegram updates, когда они реально нужны. Напоминания могут отправляться worker через Bot API без отдельного polling-процесса в 0.2.
- Сборки исполняются GitHub Actions, backup — отдельной операторской командой/таймером по ADR 0015. В app scheduler допустима проверка их результатов, но не передача worker привилегированного доступа ко всему серверу.

Scheduler и worker используют один образ и application services CMS, но отдельные entrypoints. Таблицы и migrations принадлежат CMS. Бот не импортирует их приватные модели и не ведёт вторую БД редакционных статусов.

Каждый процесс создаёт свой Dishka container из согласованных providers по ADR 0011. На отдельное задание или scheduler-операцию открывается новый `REQUEST` scope; entrypoint получает application service через контейнер и закрывает scope после выполнения, включая ошибки. Application service не знает о контейнере. Actor context и mutable зависимости не разделяются между заданиями; app-scoped клиенты закрываются при shutdown.

#### 2. Durable данные и резервирование

В БД хранятся due time, operation kind, версия payload, stable key, состояние, попытки и lease. Регулярный tick имеет ключ «правило × период», а материал/получатель — собственный delivery key. История cron-тиков сама по себе не считается историей доставок.

Worker выбирает ограниченный batch готовых строк короткой транзакцией с `select_for_update(skip_locked=True)`, фиксирует lease и освобождает блокировку до I/O. Запись результата требует актуального lease token. Старый процесс не может подтвердить чужую попытку. Timeout операции меньше lease с запасом; длительные операции не исполняются под бесконечной бронью.

Два случайно запущенных scheduler не должны создавать дублей: unique constraints обязательны даже при одном штатном экземпляре. Масштабировать worker до нескольких можно только после конкурентных тестов; deployment с одной репликой не заменяет блокировки.

Истёкшая lease до внешнего вызова позволяет безопасно переоценить задачу. Если эффект мог начаться, используется `unknown` и reconciliation ADR 0012. Рестарт не превращает все `processing` в автоматически повторяемые.

#### 3. Время, просрочка и catch-up

- Моменты времени хранятся timezone-aware в UTC; редакционный timezone задаётся явно и показывается в UI. Нельзя молча использовать timezone хоста/VPS.
- Плановая **дата** отделена от точного времени отложенной публикации. Для PLAN-03 дата считается прошедшей после окончания календарного дня в редакционном timezone. Это предлагаемая детализация для согласования с владельцем PRD, не основание сделать материал просроченным утром указанного дня.
- Напоминание «за N дней» рассчитывается по календарным датам, с явно заданным временем отправки; scheduled article — по точному timestamp.
- Просроченная scheduled article после рестарта заново проходит application service: проверка актуального одобрения, статуса, версии и запрета публикации при отмене. Старое намерение не публикует отредактированный черновик.
- Материализатор напоминает только об актуальном сроке/ответственном. Несколько пропущенных однотипных напоминаний схлопываются в одно актуальное, чтобы не залить пользователя историческими сообщениями. Повторное просрочное уведомление на каждом tick не создаётся.
- RSS catch-up проверяет доступную историю согласно ADR 0012. Экспорт/backup после простоя выполняют актуальный пропущенный запуск без бесполезного повтора каждого прошедшего дня.

#### 4. Lifecycle и эксплуатация

Tick interval и batch size ограничены настройками; начальный ориентир — tick порядка минуты, не обещание real-time SLA. Worker не делает busy polling при пустой очереди или ошибке БД. Исключение одной задачи не останавливает обработку остальных.

На SIGTERM процесс прекращает брать новые записи, завершает/корректно оставляет текущую попытку и закрывает соединения. Scheduler и worker записывают heartbeat **после успешного цикла**, включая пустую очередь. Одно наличие PID не доказывает прогресс.

Диагностика: timestamp последнего цикла, возраст самой старой due-задачи, `failed/unknown`, последняя успешная выгрузка и pending desired revision сборки. JSON stdout и доступная оператору команда/страница состояния достаточны; Prometheus/Grafana не добавляются.

#### 5. Сравнение вариантов

| Вариант | Плюсы | Минусы | Выбор |
| --- | --- | --- | --- |
| PostgreSQL state + scheduler/worker commands | Уже есть БД, единый commit/outbox, нет брокера | Нужно реализовать небольшой lease/retry loop и следить за backlog | Начальный вариант |
| System cron/timer вызывает one-shot commands | Мало application-процессов, удобно для backup | Сам не хранит задания/попытки; отдельная host-конфигурация, пересечения и пропуски требуют защиты | Для backup; возможный launcher тех же DB-backed команд |
| Готовая PostgreSQL-backed очередь | Меньше собственного runtime-кода, готовые claim/retry | Зависимость, совместимость Django/ORM, migrations и неизвестные гарантии внешних эффектов | Кандидат при росте, после spike |
| TaskIQ/Celery с Redis/RabbitMQ | Богатая экосистема, известный runtime | Ещё один сервис; Redis исключён PRD; RabbitMQ требует оценки ресурсов и восстановления | TaskIQ с RabbitMQ — кандидат для сравнения |
| In-process scheduler / in-memory очередь | Очень простой прототип | Зависимость от web/polling, потеря задач, дубли при репликах | Не для production |

Выбор готовой библиотеки в будущем требует явного описания транспорта, проверки связи с transactional outbox, восстановления и совместимости с поддерживаемыми версиями стека. Привычность библиотеки сама по себе не основание переносить Redis.

#### 6. Этапы и проверка

0.1 не требует БД и фоновых app-процессов. В 0.2 вводятся due-materializer и delivery worker; в 0.3 — RSS poll; в 0.4 — scheduled publish, export и build reconciliation. Универсальный DAG, произвольный Python из payload и динамическая регистрация задач не нужны.

Приёмка: один due key при двух scheduler, независимый claim двумя worker, корректный SIGTERM, restarts до/после I/O, heartbeat при отсутствии задач, восстановление после недоступной БД, календарная граница и timezone, смена срока/ответственного, отмена scheduled article, повторяемость tick без дублирования. Lease/blocking тесты выполняются на PostgreSQL с реальными конкурирующими соединениями, не SQLite/mocks.

## Альтернативы

Сравнение приведено в таблице выше. Выбранный компромисс — небольшая DB-backed реализация под известные задачи. Если она начинает воспроизводить произвольные цепочки, routing, распределённые лимиты и управление большим числом worker, следует перейти к готовому runtime через новый ADR, а не расширять собственный framework.

## Последствия

### Положительные

- [+] Задачи переживают рестарты, не требуют Redis и не блокируют HTTP/polling.
- [+] Семантика доставки едина для scheduler, ручного запуска и worker.
- [+] Можно сменить launcher/очередь, сохранив outbox и application services.

### Отрицательные

- [-] Lease, retries, cleanup и диагностика остаются ответственностью команды.
- [-] PostgreSQL становится общей зависимостью CMS и фонового выполнения.
- [-] Публикация и уведомления имеют ограниченную задержку, не гарантированный real-time.

Пересмотр: backlog не укладывается в согласованную задержку, нужны многие worker, сложные зависимости задач или собственный runtime стал дороже поддерживаемой библиотеки. Redis остаётся изменением PRD, а не побочным эффектом установки пакета.
