# ADR 0007: Монорепозиторий для сайта, микро-CMS и бота

## Дата: 20-11-2026

## Статус: Accepted

Принято владельцем проекта 22-11-2026.

## Контекст

Система состоит из нескольких частей:

- статический сайт на Astro (ADR 0001);
- фронтенд микро-CMS на React из Digital-hire-reports (ADR 0004);
- бэкенд микро-CMS на Django + DMR (ADR 0004);
- Telegram-бот для уведомлений, автопостинга и предложки (ADR 0004);
- общие remark-плагины с директивами и общие стили статьи, которые нужны и сайту, и превью в CMS (ADR 0002, ADR 0008).

В 0.1 статьи, метаданные и локальные медиа лежат в Git. Сайт собирается из apps/site/src/content/ на чистом checkout без API, БД и учётных данных CMS. Общий контракт и примеры материалов определены в ADR 0014.

Контент-план 0.2 можно разрабатывать параллельно. Переход сайта на опубликованный API происходит в 0.4, когда CMS и файловый загрузчик дают эквивалентный результат на общих примерах. После переключения БД CMS становится источником опубликованных материалов, файловый формат служит для экспорта и восстановления (ADR 0008).

Состав и ответственность команды описаны в CONTRIBUTING.md. Код частично пишется с помощью ИИ, и автор проекта не всегда доступен для ревью.

Нужно решить, как разложить всё это по репозиториям.

## Решение

Принято решение использовать **один монорепозиторий** для всех частей системы, потому что:

- общие пакеты (`remark-directives`, `article-styles`) подключаются локально через workspace, без публикации и синхронизации версий, поэтому превью в CMS гарантированно совпадает с сайтом;
- новая директива добавляется одним PR сразу в сайт, превью CMS и памятку для авторов;
- схема статьи (zod в Astro и схемы DMR в API) меняется атомарно в одном PR;
- один CI, одно место для ADR, архитектурного манифеста и документации по передаче проекта;
- новому участнику нужно клонировать один репозиторий, чтобы увидеть систему целиком.

### Детали реализации

1. Структура:

   ```
   apps/
     site/                # Astro: файлы в 0.1, опубликованный API в 0.4
     cms-web/             # React (из DHR)
     cms-api/             # Django + DMR
     bot/                 # aiogram: уведомления, автопостинг, предложка
   packages/
     remark-directives/   # общий для site и cms-web
     article-styles/      # общие стили статьи для сайта и превью
   docs/
     adr/
     architecture.md
   ```

2. Инструменты: **pnpm workspaces** для JS/TS (`site`, `cms-web`, `packages/*`), **uv workspace** для Python (`cms-api`, `bot`). Nx, Turborepo и подобные не используются: при таком размере они не окупаются.
3. **CI по затронутым компонентам.** Каждый PR получает итоговый статус. Ошибка обязательной для этого изменения проверки блокирует слияние. Изменения контента и медиа запускают проверку и сборку сайта. Изменения общих пакетов, контрактов, lockfile и workspace-конфигурации проверяют затронутых существующих потребителей. С появлением CMS и бота подключаются их проверки (ADR 0015).
   
   **Три примера приёмки.** Эти сценарии иллюстрируют результат. Список открыт. Костя выбирает структуру jobs, названия команд и способ отбора проверок.
   
   - Изменена только документация — итоговый статус завершается.
   - Обязательная сборка сайта упала — итоговый статус красный.
   - Изменён общий контракт или lockfile — проверки охватывают его действующих потребителей.
4. **Сборка сайта при публикации** с переходом на редакцию в 0.4 запускается из CMS через `workflow_dispatch` (ADR 0008). Это отдельный workflow, не связанный с PR.
5. **CODEOWNERS**: `docs/adr/` — автор проекта (продакт и архитектор), остальное — разработчики по зонам.
6. **Защита `main`**: только через PR, обязательные проверки CI.

## Альтернативы

* **Отдельные репозитории (polyrepo) для site, cms-web, cms-api, bot:**
  * *Плюсы:* изолированные права и история, независимые CI, проще раздать доступы по частям.
  * *Минусы:* общие пакеты нужно публиковать (npm или git-зависимость) и синхронизировать версии между сайтом и CMS, иначе превью разойдётся с сайтом. Изменение директивы или схемы статьи превращается в цепочку PR в разные репозитории. ADR и документация разбросаны. Для текущей команды это лишняя координация.

* **Монорепозиторий кода + отдельный репозиторий для контента:**
  * *Плюсы:* история статей отделена от истории кода.
  * *Минусы:* неактуально после ADR 0008: контент живёт в базе CMS, а экспорт-страховка хранится вместе с бэкапами. Если CMS выведут из эксплуатации и вернутся к файлам, вопрос пересматривается.

* **Инструменты монорепозиториев (Nx, Turborepo):**
  * *Плюсы:* граф зависимостей, кэширование сборок, запуск только затронутых проектов.
  * *Минусы:* ещё один слой конфигурации, который нужно понимать и сопровождать. Фильтров по путям в CI и workspaces при таком размере достаточно.

## Последствия

### Положительные

* [+] Превью в CMS и сайт гарантированно используют одну версию директив и стилей.
* [+] Сквозные изменения (схема статьи, новая вставка) делаются одним атомарным PR.
* [+] В MVP правки материалов проходят через PR; с переходом на редакцию в CMS публикация выполняется из панели.
* [+] Вся документация и ADR в одном месте, проще передать проект после 2027 года.
* [+] Один CI и один набор правил для всей команды.

### Отрицательные

* [-] Конфигурацию CI с фильтрами по путям нужно поддерживать при добавлении новых частей.
* [-] Два менеджера пакетов (pnpm и uv) в одном репозитории.
* [-] Все участники видят весь код. Для студенческого проекта это скорее плюс, но разграничить доступ по частям нельзя.
