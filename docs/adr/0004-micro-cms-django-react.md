# ADR 0004: Микро-CMS — панель контент-плана и редакция; React из Digital-hire-reports + Django/DMR; бот для уведомлений, автопостинга и предложки

## Дата: 21-11-2026

## Статус: Accepted

Принято владельцем проекта 22-11-2026.

Актуализация: 23-11-2026. Дополнен эксплуатационный контракт CMS для эпика #14; исходный продуктовый объём и решения DMR/Dishka, транзакций и доставки сохранены.

## Контекст

Нужен внутренний инструмент медийки, который решает две задачи:

1. **Контент-план** (запрос руководства клуба, Панасеня, 20-11-2026). Нужна панель, где видно, что запланировано, кто отвечает, к какому сроку, и что просрочено, без звонков с вопросом «где ролик про перфокарты?». Позже материалы должны публиковаться не только на сайт, но и в соцсети. Работать нужно поэтапно, чтобы пользоваться можно было уже с первых версий.
2. **Редакция статей** (ADR 0008): авторы сдают статьи, а редактор их согласует и публикует, без Git и без аккаунтов на GitHub.

**Требования главы медийки (опрос 20-11-2026):**

- Путь статьи: **автор → редактор → публикация**. Ступень проверки одна: редактор и корректор — одно лицо.
- Сейчас редактор один (глава медийки), в будущем «парочка». Авторов около трёх на старте, 5–6 через полгода.
- Комментарии к конкретным местам текста не нужны: правки обсуждаются с автором напрямую.
- Отложенная публикация нужна.
- Опубликованное могут поправить редакция и доверенные авторы (те, кто администрирует паблики медийки).
- Соавторство возможно. Гостевые материалы (преподаватели, выпускники, внешние авторы) приходят через предложку, почту или паблики, аккаунта в CMS у гостя нет.
- Автопостинг в **Telegram-канал и VK**.
- **Предложка анонимная**, разбирает редакция.

**Требования колледжа:** мат запрещён, отдельной ступени модерации нет, вопросы задаются постфактум главе медийки.

**Исходные условия команды:**

- Digital-hire-reports — фронтенд-прототип на Vite, React, TypeScript, React Router, Tailwind, shadcn/ui и react-markdown. В нём есть реестр сущностей с фильтром по этапу, статусы, редактор с правкой и превью, согласование, очередь задач на дашборде.
- В том же репозитории лежит Django-заготовка (`manage.py`, `apps/`, `config/`, tach).
- Telegram-боты автора проекта (PyBot, University Match) с модулем уведомлений на портах и адаптерах и автопостингом по крону.
- Полноценно React в команде никто не знает. Планируется ментор по React (ревью и рекомендации без участия в разработке).

## Решение

Принято решение **сделать микро-CMS с двумя модулями — «Контент-план» и «Редакция» — на React-фронтенде из Digital-hire-reports и бэкенде Django + django-modern-rest (DMR)**. Главная сущность — **материал любого типа** (`Content`, ADR 0010), а не статья. Telegram-бот используется для уведомлений, напоминаний, автопостинга и анонимной предложки.

Причины:

- контент-план и редакция работают с одной сущностью: статья — это материал, у которого есть текст. Один реестр, одни статусы, один дашборд;
- реестр, статусы, дашборд и редактор из DHR закрывают оба модуля почти без новой UI-работы;
- контент-план полезен уже без редактора статей. Его можно выпустить рано (версия 0.2) и дать бэкенду работу параллельно с сайтом;
- Django даёт роли, миграции и админку для разработчиков;
- редактировать кнопками в Telegram неудобно, а напоминать и оповещать удобно.

### Детали реализации

1. **Модель материала** — `Content` с `ContentKind` (статья, видео, подкаст, пост) и payload по типу (ADR 0010). Общие поля: название, тип, рубрика, ответственный и соавторы, плановая дата (`Deadline`), статус, внешняя ссылка на опубликованный материал.
2. **Статусы материала:**

   ```
   idea → in_progress → in_review → approved → scheduled → published
                 ↑            │
                 └─ changes_requested
   (любой статус до published) → cancelled
   ```

   - для статьи `in_review → approved` обязательны, публикует редактор;
   - для видео, подкаста и поста ступень проверки необязательна: в `published` материал переходит, когда добавлена ссылка на опубликованный материал (правила по типу описаны в ADR 0010);
   - «просрочено» — не статус, а вычисляемый признак: `Deadline.is_overdue(now)` при статусе не `published` и не `cancelled`;
   - переходы — методы доменной модели, недопустимый переход выбрасывает доменное исключение.
3. **Модуль «Контент-план»** (версия 0.2):
   - реестр материалов с фильтрами по типу, статусу, ответственному, рубрике и «только просроченные»;
   - дашборд: ближайшие сроки, просроченные, недавно опубликованные (очередь из DHR);
   - календарный или недельный вид — по запросу, не в первой версии.
4. **Модуль «Редакция»** (версия 0.4):
   - редактор статьи (правка и превью, react-markdown с общими remark-плагинами из ADR 0002);
   - очередь проверки для редактора, отправка на правки с необязательной общей заметкой (без комментариев к фрагментам);
   - `ArticleVersion` — история правок, в том числе после публикации;
   - отложенная публикация, публикация запускает сборку сайта (ADR 0008);
   - валидация при отправке: frontmatter, директивы, проверка на обсценную лексику (только предупреждает, не блокирует).
5. **Роли:**
   - `author` — свои материалы: создать, вести по статусам, отправить на проверку;
   - `trusted_author` — то же плюс правка своих опубликованных статей;
   - `editor` — все материалы: проверка, одобрение, публикация, отложенная публикация, правка опубликованного, разбор предложки, ввод гостевых материалов;
   - `observer` — **только чтение** контент-плана и дашборда (руководство клуба);
   - `admin` — пользователи и роли (админка Django).
6. **Авторы** — связь многие-ко-многим. Автор — пользователь CMS или `GuestAuthor` (имя, подпись, ссылка) без аккаунта.
7. **Аутентификация** — Telegram Login по приглашению с ролью, привязка к Telegram-ID (ADR 0009).
8. **Уведомления и напоминания** (модуль уведомлений из PyBot, новый адаптер Django → Telegram Bot API):
   - ответственному — за N дней до срока и при просрочке;
   - редактору — материал отправлен на проверку;
   - автору — отправлено на правки, одобрено, опубликовано;
   - наблюдателю — по желанию недельная сводка: что вышло, что просрочено;
   - напоминания и сводки — фоновые операции с восстановлением после сбоя по ADR 0012. Выбор исполнителя открыт в [ADR 0013](0013-background-runtime.md), не in-memory cron внутри web/polling.
9. **Автопостинг** в Telegram-канал и VK: переносится подход PyBot к портам и адаптерам, конкретный транспорт и исполнитель будут выбраны в ADR 0013. Источник новых материалов — RSS фактически выложенного сайта. За `PublisherPort` стоят адаптеры Telegram Bot API и VK API. Кросспостинг видео и постов, которых нет на сайте, — позже, тоже через `PublisherPort`. Загрузка роликов на YouTube и Rutube не автоматизируется.
10. **Анонимная предложка:** диалог на aiogram-dialog (тема и описание). Редакция видит предложение без данных отправителя, связь с Telegram-ID хранится только в боте, чтобы можно было ответить. Принятое предложение превращается в материал со статусом `idea`.
11. **Бэкенд:** Django + **django-modern-rest (DMR)**, PostgreSQL, **Dishka DI/IoC** через `dmr-dishka`. DMR controllers принимают/возвращают типизированные схемы msgspec или Pydantic, application services внедряются через `FromDishka`, а не создаются в endpoint. OpenAPI генерируется из DMR и служит источником TS-клиента React. Published snapshot API и намерение сборки через `workflow_dispatch` описаны в [ADR 0008](0008-db-source-of-truth.md). Lifecycle/config соответствуют 12 Factor и ADR 0015.
12. **Перенос из Digital-hire-reports:**
    - реестр кандидатов с фильтром по этапу → реестр материалов с фильтрами;
    - этапы найма → статусы материала;
    - дашборд с очередью задач → дашборд контент-плана и очередь редактора;
    - редактор отчёта → редактор статьи;
    - согласование отчёта → проверка и публикация;
    - плейсхолдеры пустых полей → подсказки валидации;
    - Biome, tsc, Vitest — без изменений.
    - Выкидывается: 1С, найм, интервью, генерация отчётов.
13. **Ревью React-кода:** ментор по React периодически смотрит код и даёт рекомендации. Они фиксируются в `AGENTS.md` и в чек-листе ревью, чтобы их учитывали и команда, и ИИ-ассистенты. Рабочим примером служит код DHR.

#### Application services, DI/IoC и транзакции

- Граф зависимостей собирается Dishka providers в модуле `di`: настройки, persistence, port adapters, application services. HTTP composition root подключает DMR integration; бот использует aiogram integration; management commands, scheduler и worker создают scopes явно. Подробный контракт — [ADR 0011](0011-application-architecture-and-boundaries.md).
- `APP` — проверенные настройки, безопасно переиспользуемые SDK-клиенты/адаптеры и stateless persistence-компоненты; `REQUEST` — application service и actor context отдельного HTTP-запроса/update/задачи. Финализация request и app ресурсов выполняется даже при ошибках. Контейнер не передаётся в бизнес-логику как service locator.
- DMR controller выполняет transport parsing, вызывает use case и формирует безопасный response. Переходы статусов, публикация, приглашения и изменение ролей не реализуются в controllers/serializers; они обращаются к application services.
- Application service проверяет object-level authorization, блокирует/проверяет актуальную ревизию материала, вызывает rich model и управляет `transaction.atomic`. Повторное обращение к use case не должно менять чужой материал или публиковать устаревшую версию.
- Изменение модели, обязательная запись аудита операции и намерение внешнего эффекта сохраняются в одной транзакции. Все Telegram/VK/GitHub вызовы — вне неё, через outbox/worker по [ADR 0012](0012-reliable-external-effects.md). `on_commit` — только необязательное пробуждение worker, не единственное место хранения намерения.
- Django ORM управляет соединениями штатно; SQLAlchemy session и Alembic из PyBot не переносятся. DI scope не равен транзакции. Критическая orchestration запрещена в signals, `save()`-хуках и middleware.
- Django admin actions, импорт и фоновые команды вызывают те же use cases для бизнес-переходов. Обычные bulk update не обходят модель/сервис; контролируемые data migrations описываются отдельно. Технический admin не становится редактором автоматически.
- Session auth и CSRF на DMR включаются явно по [ADR 0009](0009-authentication.md); DI не заменяет authentication/authorization. Строгие request/response/error schemas не допускают утечки ORM/SDK исключений.

#### Эксплуатационный контракт CMS

Связано с эпиком [#14](https://github.com/Sreda-Media/sreda-media/issues/14) и требованиями NFR-OPS-01–04. CMS обеспечивает следующие интерфейсы для эксплуатационной инфраструктуры по [ADR 0005](0005-observability-glitchtip.md) и [ADR 0015](0015-runtime-and-data-operations.md):

- С 0.2 Django/DMR предоставляет /healthz без обращения к БД и /readyz с ограниченной по времени проверкой PostgreSQL и реально используемого хранилища. Проверяются 200 при liveness и 503 при отказе обязательной зависимости. Ответ содержит только безопасный статус и код.
- Backend реализует структурированные JSON-события stdout с event, component, operation, outcome, timestamp, environment, release и correlation ID. Идентификатор связывает запрос, use case, фоновые операции и попытки доставки. Логи не содержат секретов, содержимого материалов/предложки и персональных данных; редакционный audit хранится отдельно.
- Worker и scheduler публикуют progress heartbeat и события успешных/неуспешных циклов. Выбор транспорта остаётся в ADR 0013. Sentry SDK для GlitchTip подключается при появлении соответствующих backend-процессов по NFR-OPS-01; на 0.3 покрытие расширяется на автопостинг. Если tracker не готов, применяется только согласованное исключение ADR 0005.
- Отказ мониторинга, error tracker или сборщика логов не влияет на readiness, бизнес-транзакции и последнюю опубликованную витрину. Инструментирование подключается в composition root/transport и инфраструктурных адаптерах, не привязывает домен к конкретному observability stack.
- DevOps отвечает за сбор/хранение телеметрии, алёрты, backup и restore; Backend обеспечивает интерфейсы, очистку данных и тестовые сценарии. С 0.2 проверяется ежедневный backup PostgreSQL и восстановление; с 0.4 — согласованность БД и медиа, сборка из опубликованного экспорта без CMS. Порядок, ресурсные ограничения и runbook определяются ADR 0005, 0015.
- Целевой стек из эпика #14 (Uptime Kuma, Grafana + Alloy + Loki, GlitchTip) требует актуализации ADR 0005 и согласованных связанных ограничений до реализации конфликтующих решений. В этом ADR фиксируются обязанности CMS; конкретная конфигурация инфраструктуры остаётся у DevOps.

#### Готовность по этапам

- 0.1: только статическая витрина; CMS/DI-контейнер Python не нужны для её сборки.
- 0.2: один полный DMR → Dishka service → rich model → PostgreSQL slice, матрица доступа и outbox уведомлений.
- 0.3: независимые доставки Telegram/VK, дедупликация и catch-up по выложенному RSS. Ошибка одной площадки не отменяет успех другой.
- 0.4: версии статей, snapshots, shared validation и сборка по ADR 0008/0014. Редакционный `published` отделён от подтверждения deploy.

Проверки будущей реализации: request scope изолирует actor между пользователями, provider override подменяет SDK, rollback не оставляет уведомление, admin/worker не обходят права и переходы, ошибка DMR превращается в безопасный transport response. Сигналы не являются скрытым источником внешних эффектов.

## Альтернативы

* **Готовый таск-трекер для контент-плана (Notion, Kaiten, Яндекс Трекер, GitHub Projects):**
  * *Плюсы:* ничего не нужно разрабатывать, есть доски, календари, напоминания.
  * *Минусы:* отдельный инструмент, не связанный с сайтом и публикацией. Статусы материала и статьи жили бы в двух местах. Руководство просит именно панель в системе, которая потом сама публикует на сайт и в соцсети. Годится как временное решение до версии 0.2.

* **Отдельные сущности для плана и для статьи:**
  * *Плюсы:* модули проще по отдельности.
  * *Минусы:* статья в плане и статья в редакции — один и тот же материал. Пришлось бы синхронизировать статусы и сроки между двумя сущностями. См. ADR 0010.

* **FastAPI + SQLModel вместо Django:**
  * *Плюсы:* легче, есть опыт по PyBot.
  * *Минусы:* роли, миграции (Alembic) и админку собирать вручную. Django-заготовка уже есть.

* **Django Ninja или DRF вместо DMR:**
  * *Плюсы:* зрелые, стабильное API, больше примеров.
  * *Минусы:* DRF не строго типизирован и медленнее, Ninja уступает DMR в строгости типов и проверке ответов. У DMR есть skills для миграции с них, выбор обратим.

* **htmx + Alpine.js поверх серверных шаблонов:**
  * *Плюсы:* логика на сервере, в Python, код легко ревьюить без знания React.
  * *Минусы:* редактор статей с превью и загрузкой картинок на Alpine превращается в кашу, готовый фронтенд DHR не используется. Запасной вариант, если ментора по React не будет.

* **Telegram-бот как основной интерфейс:**
  * *Плюсы:* фронтенд не нужен, все в Telegram.
  * *Минусы:* вести реестр и редактировать текст кнопками неудобно. Боту остаются уведомления, напоминания и предложка.

* **Git-based CMS (Keystatic, Decap, Sveltia):**
  * *Плюсы:* готовые решения.
  * *Минусы:* нет контент-плана, ролей, статусов и отложенной публикации, каждому автору нужен GitHub.

* **Комментарии к фрагментам текста в редакторе:**
  * *Плюсы:* привычно для редакций.
  * *Минусы:* правки обсуждаются напрямую, функция сложная (якоря в тексте съезжают при правках). Пересмотреть, когда редакторов станет несколько.

## Последствия

### Положительные

* [+] Контент-план приносит пользу руководству и главе медийки уже с версии 0.2, задолго до редактора статей.
* [+] Один реестр и одна модель для плана и редакции, синхронизировать нечего.
* [+] Большая часть UI уже есть в DHR.
* [+] Напоминания о сроках снимают необходимость звонить и спрашивать.
* [+] Переиспользуется код PyBot. Порты и адаптеры позволяют добавить VK и другие площадки без правок домена.
* [+] Бэкенд работает параллельно с сайтом, а не простаивает.

### Отрицательные

* [-] Два стека (TS и Python) и два деплоя (сайт и CMS) плюс бот.
* [-] Без ментора по React код, написанный ИИ, без ревью копит баги в хуках.
* [-] Вход в CMS зависит от Telegram (ADR 0009).
* [-] VK API добавляет токен сообщества и ещё одну внешнюю зависимость.
* [-] CMS — сервис с БД, который нужно сопровождать. Если он упадёт, сайт работает на последней сборке, но новые статьи не выходят (ADR 0008).
* [-] Риск расползания: календари, отчёты, аналитика по команде. Каждое расширение — отдельное решение с проверкой на реальную потребность.
