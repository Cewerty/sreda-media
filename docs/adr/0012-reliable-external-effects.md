# ADR 0012: Надёжные внешние эффекты через порты, transactional outbox и учёт попыток

## Дата: 21-11-2026

## Статус: Accepted

Принято владельцем проекта 22-11-2026.

## Контекст

Уведомления нужны в 0.2 (NOTIF-01/02), анонсы Telegram/VK — в 0.3 (PUB-01–03), отложенная публикация и пересборка — в 0.4 (EDIT-08/12). БД, Telegram, VK и GitHub Actions не участвуют в одной транзакции. Отправка до commit может сообщить об откатившемся изменении; отправка после commit без сохранённого намерения может потеряться при падении процесса.

Из PyBot переносится разделение use case, dispatch и transport adapter, но не TaskIQ/Redis. Нужны восстановление после простоя, независимый результат по каналам и честная обработка случая «запрос ушёл, подтверждение потеряно». Уникальная запись в БД не обеспечивает exactly-once на внешней площадке.

## Решение

Решено использовать **типизированные порты внешних операций и transactional outbox в PostgreSQL**. Business commit сохраняет намерение; исполнитель доставляет его вне транзакции с учётом попыток, lease и результата. Гарантия — сохранность намерений и управляемые повторные попытки; однократность внешнего эффекта зависит от конкретного API.

### Детали реализации

#### 1. Порты и границы

- `NotificationPort` — адресное уведомление; `PublisherPort` — анонс на площадке; `SiteBuildPort` — запрос и сверка сборки. На входе typed command, на выходе typed outcome, не SDK response.
- Telegram/VK/GitHub adapters переводят provider-specific ошибки в `temporary_failure`, `permanent_failure` или `unknown`. Logging/fake adapters допустимы локально, но не отмечают production-доставку успешной.
- Application service получает контракт порта через constructor injection; concrete adapter, SDK-клиент и настройки связываются Dishka providers в composition root по ADR 0011. Network timeout, retry limit и credentials — параметры runtime, не методы `Content`.
- `MediaStoragePort` вводится для upload/snapshot/export в 0.4, не как универсальная файловая абстракция с 0.1.

#### 2. Durable state и commit

Изменение статуса, нужная запись бизнес-аудита и намерения доставки сохраняются в одной `transaction.atomic`. Rollback отменяет всё вместе. `on_commit` может ускорить пробуждение worker, но не заменяет outbox: после commit процесс может завершиться до callback.

Запись намерения содержит ID, вид операции, версию payload, business key, канал/назначение, ссылку на материал/ревизию, время доступности, состояние, число попыток, `next_attempt_at`, lease token/expiry, безопасную категорию последней ошибки и внешний ID при наличии. Приватное назначение доступно только исполнителю, не публичным логам. История попыток отдельна от бизнес-истории статусов.

Ключ защищён unique constraint:

- напоминание: материал × получатель × правило × ревизия срока;
- уведомление: ID перехода × получатель × вид уведомления;
- анонс: стабильный ID материала × площадка × назначение × вид «первый анонс»;
- сборка: целевая ревизия snapshot с возможностью схлопнуть промежуточные запросы.

Обновление статьи не означает повтор первого анонса. Повторная рекламная публикация — отдельный use case, не новый ключ из-за изменения текста или slug.

#### 3. Исполнение, retries и неизвестный исход

1. Worker короткой транзакцией резервирует due-запись, создаёт попытку и lease с уникальным token.
2. Проверяет актуальность: смена срока/ответственного, отмена или публикация могут сделать напоминание ненужным. Для scheduled article заново проверяются одобрение и актуальная версия.
3. Выполняет внешний вызов вне транзакции с ограниченным timeout.
4. Записывает результат только при совпадении lease token: устаревший worker не завершает попытку нового владельца.
5. Явные временные отказы повторяются с backoff, jitter и `Retry-After`, если применим. Постоянные ошибки завершаются как `failed`. Retry budget и причина остановки видны оператору.

Состояния: `pending → processing → succeeded / retry_wait / failed / unknown / cancelled`. `succeeded` требует подтверждения площадки. Истёкшая lease после начала вызова и timeout с возможным внешним успехом дают `unknown`, не автоматический повтор.

При native idempotency повтор использует тот же provider key и учитывает срок его действия. Иначе адаптер сверяет результат по correlation/external ID, если API это позволяет. При невозможности сверки оператор проверяет площадку и подтверждает успех либо повтор. Lease не является внешним fencing-механизмом и сама по себе не предотвращает дубли.

PUB-03 сохраняется как критерий выпуска: для каждого канала до 0.3 проверить стратегию дедупликации и восстановления. Если API не позволяет автоматически разрешать `unknown`, согласовать этот сценарий с владельцем требования; ручную сверку нельзя выдавать за полную автоматическую гарантию «без дублей».

#### 4. Автопостинг и частичный успех

Источник в 0.3 — **RSS фактически выложенного сайта**, как в ADR 0004. `Content.status=published` сам по себе не запускает анонс: сайт может ещё не обновиться. RSS-item имеет стабильный GUID, не зависящий от slug.

Повторное чтение RSS создаёт недостающие намерения с unique key. Telegram и VK имеют отдельные записи: успех Telegram не скрывает отказ VK. При первом включении задаётся явная стартовая граница, чтобы не анонсировать весь архив.

До приёмки PUB-03 обеспечить полную историю RSS за поддерживаемый период простоя либо статический manifest всех опубликованных материалов для сверки. Один cursor и ограниченная лента не гарантируют восстановление пропущенного.

#### 5. Сборка и публикация в 0.4

Редакционный `published` по ADR 0008 означает включение в желаемый published snapshot. Фактическая выкладка учитывается отдельно: `PublicationDeployment` с desired/snapshot revision, request ID, workflow run ID при получении, результатом и deployed revision. Новые статусы не добавляются в редакционную машину состояний.

Сервис публикует approved version и сохраняет намерение сборки; worker группирует близкие изменения в актуальную desired revision. `workflow_dispatch` означает запрос, не deploy. Timeout сверяется по correlation ID. Workflow собирает артефакт из snapshot, проверяет его и выкладывает атомарно. Результат подтверждается аутентифицированным callback или сверкой workflow и публичного deployment manifest: одного успешного CI недостаточно.

`concurrency` GitHub Actions защищает от конкурентных выкладок, но не заменяет debounce и учёт desired revision. Старый job не должен перезаписать новый сайт: перед переключением проверяются snapshot revision и актуальная цель. Если цель изменилась за время сборки, запускается завершающая сборка актуального snapshot. Ошибка сохраняет последнюю успешную статику, а состояние выкладки показывает отставание.

Повторный deploy той же ревизии безопасен. GitHub-токен не получает `Contents: write`; workflow/ref фиксированы адаптером. `Actions: write` шире права единственного запуска: ограничение нужно согласовать по NFR-SEC-04, не объявлять это разрешение более узкой capability.

#### 6. Этапы и проверка

0.2: outbox для напоминаний/уведомлений; 0.3: per-channel анонсы; 0.4: сборки и reconciliation. Не строить универсальный EventBus или event sourcing.

Приёмка: rollback без отправки; crash после commit; два исполнителя; смена срока/ответственного; частичный отказ VK; повторное чтение RSS; простой дольше видимой ленты; внешний успех с падением до сохранения результата; истёкшая lease без слепого повтора; stale/failed build без повреждения статики. Возможности конкретных API проверяются адаптерными contract-тестами до обещания PUB-03.

## Альтернативы

- **Отправка внутри HTTP-транзакции.** Плюс: мало кода. Минусы: длинные блокировки, внешний эффект нельзя откатить вместе с БД.
- **Только `on_commit`.** Плюс: эффект не произойдёт до commit. Минус: намерение теряется при падении между commit и вызовом.
- **Брокер без outbox.** Плюс: готовая доставка задач. Минусы: dual write и неизвестный внешний результат остаются; Redis запрещён PRD.
- **Слепой at-least-once retry.** Плюс: проще догонять пропуски. Минус: дубли после потерянного подтверждения нарушают PUB-03.

## Последствия

### Положительные

- [+] Commit не теряет намерение; Telegram/VK восстанавливаются независимо.
- [+] Состояние сайта отделено от редакционного решения.
- [+] Сетевые сбои и восстановление становятся диагностируемыми.

### Отрицательные

- [-] Нужны delivery state, история попыток, reconciliation и операторская процедура.
- [-] Exactly-once нельзя обеспечить одной PostgreSQL-таблицей для произвольного API.
- [-] UI различает принятие операции и её фактическое выполнение; доставка eventual.

Пересмотр: объём задач требует брокера или provider idempotency меняется. Outbox и границы транзакций сохраняются при замене runtime.
