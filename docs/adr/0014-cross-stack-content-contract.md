# ADR 0014: Версионированный контракт контента между Django, React, Astro и файловым экспортом

## Дата: 21-11-2026

## Статус: Accepted

Принято владельцем проекта 22-11-2026.

## Контекст

В 0.1 материалы хранятся файлами; в 0.4 сайт начинает собираться из read-only API CMS. Ночной экспорт должен позволять вернуться к файловой сборке без CMS (CONTENT-05, NFR-OPS-03, ADR 0008). React-preview и Astro используют общий Markdown-синтаксис и стили (EDIT-01, ADR 0002/0007).

Фраза «схема та же» недостаточна: Python, TypeScript и Zod — разные реализации. OpenAPI-клиент даёт типы, но сам по себе не валидирует JSON во время сборки. Общие remark-плагины тоже не гарантируют одинаковые sanitization, CSS и работу изображений. Изменение поля, директивы или пути может сломать экспорт, импорт или ранее опубликованную статью.

Основания: CONTENT-01–05, SITE-04–07, EDIT-01/03/09/12, NFR-AVAIL-01, NFR-OPS-03, NFR-MAINT-01/02.

## Решение

Решено определить **один версионированный публичный content contract**, общий для файлов, опубликованного API и экспорта. Структурный формат фиксируется JSON Schema; Django/DMR и Astro валидируют свои границы, а CI проверяет общие положительные и отрицательные fixtures. Редакционные команды и приватные данные не смешиваются с published snapshot.

### Детали реализации

#### 1. Владение и расположение

- Контракт принадлежит проекту медийки, ответственным является владелец архитектуры совместно с владельцами backend/site; изменение требует ревью обоих потребителей.
- Предлагаемый пакет `packages/content-contract` содержит каноническую JSON Schema публичного формата, описание семантики и fixtures. Он добавляется в монорепозиторий ADR 0007; Python читает JSON как ресурс, не импортирует TS-пакет.
- Начальная версия формата — `schema_version: 1`. Структурные ограничения задаются схемой; межзаписные правила и Markdown-семантика — документированным контрактом и тестами. Ни Python serializer, ни Zod не считаются автоматически эквивалентными схеме.
- `packages/remark-directives` и `packages/article-styles` остаются из ADR 0002/0007; контентный пакет не становится складом общей бизнес-логики CMS.

Владение файлами и обязательные проверки закрепляются в CODEOWNERS/CI. При переносе этот ADR дополняет ADR 0007 новым общим пакетом, не меняет выбор pnpm/uv workspaces.

#### 2. Public model и стабильная идентичность

Для страниц статьи и видео в 0.1 каноническая форма записи задана в [JSON Schema v1](../../packages/content-contract/published-site-record.v1.schema.json). Примеры [статьи](../../packages/content-contract/examples/article.json) и [видео](../../packages/content-contract/examples/video.json) используют одну рубрику. Это нормализованный результат загрузки, одинаковый для файлов и будущего published API.

| Поле | Семантика |
| --- | --- |
| `schema_version`, `id`, `slug` | Версия публичного формата, стабильный строковый ключ материала и сегмент публичного URL. ID создаётся независимо от slug и сохраняется при переименовании. |
| `kind`, `payload` | `kind` выбирает схему содержимого. Для `article` тело файла `.md` целиком попадает в `payload.markdown`; в CMS источником того же поля служит текст выбранной одобренной версии. Для `video` frontmatter содержит `payload.url` и `payload.description`; сборщик проверяет ссылку на поддерживаемый ролик VK, Rutube или YouTube. |
| `title`, `rubric_id`, `author_ids` | Заголовок, ключ единственной рубрики и упорядоченные ключи публичных авторских профилей. Для статьи нужна хотя бы одна подпись, у видео допустим пустой список. Гостя можно указать без аккаунта. |
| `published_at` | Момент редакционной публикации в RFC 3339 с `Z` или явным смещением. Сборщик проверяет формат даты и сравнивает моменты времени с учётом смещения. Повторная сборка сохраняет дату публикации. |
| `cover` | Объект с относительным путём `path` к изображению в media manifest и текстом `alt`. Для статьи обязателен, у видео без обложки поле опускается. |

Astro строит карточку ленты и метаданные из публичной записи. Правила формирования Open Graph-превью и критерии приёмки определены в [спецификации SITE-13](../specs/site-13-open-graph.md). Отдельные поля для социального превью не входят в public contract v1.

Послесловие статьи можно написать в Markdown, авторскую подпись сайт строит по `author_ids`. Поля `footer`, `content`, `preview_img` и `tags` в v1 отсутствуют. Теги остаются возможным расширением для тематической подборки материалов из разных рубрик; добавление проходит проверку совместимости по §4.

В модели редакции также предусмотрены `podcast` и `post` (CONTENT-01, ADR 0010). Схема по ссылке описывает материалы, выводимые на сайте в 0.1. Расширение набора страниц потребует согласовать публичный payload и поддержку потребителей. Версионирование внутреннего payload и правила перехода публичного контракта описаны в §4.

Public author profile содержит только предназначенные для сайта поля. В snapshot/экспорт не попадают Telegram ID, provider identity, права сотрудников, приглашения, приватные сроки/заметки и черновики. DTO публичной страницы не является сериализацией всей Django-модели.

Ссылочная целостность (рубрика/авторы существуют), unique ID/slug, timezone/date semantics и допустимость payload проверяются отдельно от простой JSON Schema. Переименование опубликованного slug требует явного решения о redirect; не заменяет идентификатор и не вызывает повторный анонс.

#### 3. Три формы одного содержания

| Форма | Где применяется | Проверка |
| --- | --- | --- |
| `.md` с frontmatter + локальные медиа и справочники | MVP 0.1, экспорт, аварийная сборка | Parse → нормализованный public record → schema/semantic validation |
| JSON published snapshot + manifest | Read-only API CMS с 0.4 | Runtime validation и ссылки на immutable media |
| DMR response schema / TS client / Zod collection schema | HTTP и потребители | Проверка против canonical fixtures и generated-artifact drift |

Каждый loader преобразует источник в одинаковую нормализованную модель. Страницы Astro не узнают, прочитан файл или API. Формат медиа/справочников определяется уже для MVP, не откладывается до импорта в CMS.

OpenAPI генерируется из фактических DMR routes/schemas и является источником типизированного клиента React. Published API использует явное соответствие public contract; CI проверяет response fixtures и отсутствие расхождений. Генерация клиента воспроизводима и фиксирована lockfile; ручные правки generated files запрещены.

Astro сохраняет Zod validation по ADR 0001/0008 и валидирует входные данные до записи в collection. JSON Schema — канон wire-формата; Zod — адаптер Astro, не второй независимый источник правил. Автоматический генератор допускается только после проверки поддерживаемого подмножества; до этого соответствие подтверждается fixtures и review, не обещанием полной формальной эквивалентности.

#### 4. Snapshot, версии и миграции

Read-only build API возвращает immutable snapshot опубликованного набора с `schema_version`, `snapshot_id`, временем создания, списком материалов/справочников и media manifest. Пагинация привязана к snapshot; последовательные страницы не читают разные состояния live DB.

Snapshot формируется из согласованного состояния данных; опубликованная версия и её media references не меняются на месте. Editing создаёт новую ревизию, а не изменяет содержимое артефакта уже запущенной сборки. Хранение/очистка snapshots должны учитывать ещё работающие workflow и текущую выкладку.

Неизвестная версия формата останавливает импорт/сборку с понятной диагностикой. Изменения значений enum, обязательности или смысла поля требуют новой версии и явного преобразования. Добавление опционального поля также проходит CI совместимости; поддерживаемые readers/writers указываются в контракте, не подразумеваются.

Не требуется постоянная поддержка всех старых форматов. Для breaking release сначала поставляется совместимый reader, затем writer; старый формат удаляется после проверки exports и in-flight builds. Версия payload в БД из ADR 0010, версия API и content schema — разные контракты, их нельзя молча приравнивать.

#### 5. Markdown, preview и медиа

- Одинаковые remark-плагины, список директив, правила атрибутов и article styles используются site/cms-web из одного workspace lockfile. Unknown directive или отсутствующий обязательный атрибут — ошибка, не тихий fallback.
- Preview использует тот же pipeline validation; обязательная серверная проверка не доверяет React. Python проверяет metadata, а директивы проверяются общей JS-реализацией через ограниченный validator entrypoint. Не писать второй независимый regex-парсер в Python.
- В 0.4 validator поставляется версионированным CLI/модулем из общего пакета и вызывается адаптером с timeout и структурированной диагностикой. Это build/runtime-зависимость редакции; версия проверяется CI и входит в ресурсный бюджет.
- Raw HTML и пользовательский JS не исполняются. Для directives allowlist включает допустимые площадки и URL-схемы; URL преобразуется в безопасный embed. Картинки требуют alt, подпись не заменяет alt; пример директивы и памятка обновляются вместе.
- Нет требования идентичности всей страницы: совпадает область статьи; шапка и навигация CMS/site могут различаться. Общие browser fixtures проверяют структуру/стили статьи, а не только AST.
- Обложка, картинки статьи и необходимые изображения авторов скачиваются в build и оптимизируются. Публичный сайт не зависит от CMS для этих файлов. Намеренные внешние video/audio embeds не являются копированием/хостингом видео.
- Media manifest содержит относительный путь, тип, размер и checksum. Запрещены path traversal, приватные filesystem paths и произвольный fetch во внутреннюю сеть. Несуществующее медиа или несовпавший checksum останавливают сборку, не портят текущий deploy.

#### 6. Экспорт и contract fixtures

Ночной экспорт создаёт законченный архив опубликованного snapshot: `.md`, рубрики, авторские профили, локальные медиа и manifest с версией/checksums. Архив сначала проверяется, затем атомарно помечается завершённым. Частичный результат не считается recovery export.

Fixtures включают: все kinds; гостя и соавторов; кириллицу; границы дат; каждые directive/атрибуты; ошибочный enum, ссылку, ID, неизвестную версию; HTML/unsafe URL; отсутствующее медиа. Один набор прогоняется через Python-validator/serializer, JSON Schema, Astro loader и CMS preview.

Round-trip `файлы → импорт CMS → snapshot → экспорт → файловая сборка` сохраняет стабильные IDs и семантику контента; не требуется побайтовая идентичность YAML formatting. Сравниваются нормализованные записи, ссылки и checksum исходных медиа, а не оптимизированные выходные картинки разных toolchain.

#### 7. Этапы и проверка

0.1: canonical format, file loader, directives и fixtures, без БД/API. 0.2: OpenAPI-клиент контент-плана, без публикации draft-полей. 0.4: snapshot API, импорт/экспорт и общий validator. Переход с файлов на API допускается после успешного round-trip и сборки из экспорта при отключённой CMS.

CI запускает потребителей при изменениях всех трёх общих пакетов, контрактов API и lockfiles. Проверяет regeneration diff, положительные/отрицательные fixtures, preview/article render и аварийную сборку. Изменение схемы или директивы идёт одним PR с consumers, памяткой и migration/export impact.

## Альтернативы

- **Ручные несвязанные схемы Python/Zod.** Плюс: быстро начать. Минус: расхождения проявляются при публикации или аварийном восстановлении.
- **Только OpenAPI/TS types.** Плюс: хороший HTTP DX. Минус: не определяет Markdown, файловый экспорт и runtime-проверки контента.
- **Генерация всего из одной библиотеки без contract tests.** Плюс: меньше дублирования. Минус: различия supported features/coercion/форматов остаются незаметны.
- **MDX или произвольный HTML.** Плюс: гибкость. Минусы: нарушает ADR 0002, усложняет безопасный preview и порог входа авторов.

## Последствия

### Положительные

- [+] Файловый MVP одновременно проверяет путь отказа от CMS.
- [+] Draft/private данные отделены от публичного контента.
- [+] Изменения формата и директив видны всем потребителям в одном PR.

### Отрицательные

- [-] Нужны schema ownership, fixtures и поддержка serializer/loader adapters.
- [-] Validator добавляет JS-зависимость в контур редакции 0.4.
- [-] Snapshot/media retention и миграции формата требуют операционной дисциплины.

Пересмотр: новый потребитель/формат не укладывается в public contract или становится нужен другой редактор. Смена AST/Markdown engine требует обновить весь preview/export путь, не только сайт.
