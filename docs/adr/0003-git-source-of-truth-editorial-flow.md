# ADR 0003: Git — источник правды для опубликованного контента; редакционный процесс через PR

## Дата: 20-11-2026

## Статус: Superseded

Заменён: ADR 0008 (БД микро-CMS — источник правды). Документ сохранён как история решения: причины отказа описаны в ADR 0008, раздел «Альтернативы».

## Контекст

Сайт статический (ADR 0001), статьи — `.md`-файлы в репозитории (ADR 0002). При этом:

- авторы не умеют и не обязаны уметь работать с Git;
- редакции нужен процесс согласования: автор сдаёт статью, глава медийки смотрит, отправляет на правки или одобряет;
- для этого процесса нужна база данных (черновики, статусы, комментарии ревью).

Если база и репозиторий одновременно хранят опубликованный контент, получатся две копии, и они разъедутся. Нужно однозначно определить, где источник правды.

Вариант «авторы присылают `.md` редактору, а он коммитит руками» создаёт узкое место и лишнюю нагрузку на главу медийки. Он допустим только как временный.

## Решение

Принято решение **хранить опубликованный контент только в Git-репозитории сайта, а в базе микро-CMS — только рабочие данные редакции**, потому что тогда:

- у опубликованного контента есть история, ревью и откат средствами Git;
- сайт собирается из репозитория и не зависит от доступности CMS;
- база не может разойтись с сайтом: она не хранит то, что на сайте.

### Детали реализации

1. **В базе:** черновики, статусы, история согласования, комментарии ревью, пользователи и роли.
2. **В Git:** опубликованные `.md`, картинки (или ссылки на медиахранилище), история правок.
3. Статусы статьи: `draft` → `in_review` → `changes_requested` → `approved` → `published`.
4. Процесс:
   1. Автор пишет статью в микро-CMS и отправляет на ревью.
   2. Сервис валидирует frontmatter и директивы, создаёт ветку и открывает PR через GitHub API.
   3. CI собирает превью-деплой PR (`pr-<N>.<домен>`).
   4. Редактор смотрит превью и в CMS одобряет статью или отправляет её на правки.
   5. При одобрении сервис мержит PR, CI деплоит прод, статус меняется на `published`.
5. Правки опубликованной статьи идут тем же путём, через новый PR.
6. Превью-деплои: GitHub Actions → rsync в `/srv/previews/pr-<N>` → Caddy с wildcard-поддоменом (ADR 0006). При закрытии PR отдельный job удаляет папку.

## Альтернативы

* **База данных — источник правды, сайт тянет контент через API:**
  * *Плюсы:* привычная модель CMS, мгновенная публикация.
  * *Минусы:* сайт зависит от доступности API или требует пересборки по вебхукам. Нет истории и отката на уровне Git. По сути это headless CMS, от которой отказались в ADR 0001.

* **Двусторонняя синхронизация базы и Git:**
  * *Плюсы:* правки можно вносить и там, и там.
  * *Минусы:* конфликты, рассинхронизация, сложная логика. Неоправданно для проекта такого масштаба.

* **Ручной коммит редактором (без CMS):**
  * *Плюсы:* ничего не нужно разрабатывать.
  * *Минусы:* узкое место в лице одного человека, нагрузка на главу медийки, костыль. Допустимо только как временное решение до готовности микро-CMS.

## Последствия

### Положительные

* [+] Один источник правды для опубликованного контента, расхождения невозможны.
* [+] История, ревью и откат средствами Git бесплатно.
* [+] Редактор видит статью ровно так, как она выйдет на сайте (превью-деплой).
* [+] Если CMS упадёт, сайт работает, а статьи временно можно коммитить руками.

### Отрицательные

* [-] Публикация занимает время сборки и деплоя, не мгновенная.
* [-] Нужны токен GitHub-бота с правами на репозиторий и аккуратное хранение секретов.
* [-] Превью-деплои требуют инфраструктуры (wildcard DNS, Caddy, очистка).
