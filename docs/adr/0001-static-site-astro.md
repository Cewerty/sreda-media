# ADR 0001: Сайт медийки — статический Astro

## Дата: 20-11-2026

## Статус: Accepted

Принято владельцем проекта 22-11-2026.

## Контекст

Медиа-клубу нужен сайт. По итогам опроса главы медийки (20-11-2026) это **часть общего сайта медийки**, а не отдельный блог: описание, команда, контакты и рубрики, в которых лежат и статьи, и видео. Ориентир по подаче и оформлению — «Код» от Яндекса (thecode.media), дополнительно «Хакер» и Хабр.

Что известно о контенте и аудитории:

- **Объём.** Статья раз в 1,5–2 недели, расшифровки подкастов 1–2 раза в месяц. Форматы: обзоры, гайды, интервью, новости, расшифровки подкастов.
- **Авторы.** Около трёх на старте, 5–6 через полгода. Гостевые материалы (преподаватели, выпускники, внешние авторы) приходят через предложку или почту и публикуются с разрешения автора.
- **Аудитория.** Программисты и те, кто хочет ими стать: студенты, выпускники, работающие разработчики, в том числе сеньоры и те, кто ищет кандидатов. Аудитория внешняя, за пределами колледжа. Основное продвижение идёт через паблики: VK, Rutube, YouTube, TikTok, Instagram. Сайт — дополнительная точка.
- **Читатели.** Комментарии на сайте пока не нужны, но появятся позже, «в последний момент». Аккаунты читателей нужны: профиль с именем и аватаркой, закладки, избранные рубрики (уточнение главы медийки, 20-11-2026). Приоритет на старте — чтобы сайт работал и показывал видео.
- **Авторы.** У авторов есть публичные профили со списком их материалов.
- **Статистика** нужна авторам и редакции, руководству колледжа — нет.
- **Минимум к запуску** со слов главы медийки: описание, команда, пара рубрик с видео, контакты.
- **Дедлайна нет**: медийка сначала раскручивается на площадках.

Ограничения команды: три разработчика, состав будет меняться, автор проекта выпускается в 2027 году. Бюджета почти нет, хостинг оплачивает автор проекта (ADR 0006).

Нужно выбрать основу сайта: CMS с сервером или статическую генерацию.

## Решение

Принято решение использовать **Astro в режиме статической генерации (SSG)**. Причины:

- при статье раз в 1,5–2 недели сервер с БД под сайт не окупается;
- собранный сайт — это папка HTML, которая работает без присмотра и переживёт смену команды;
- Astro рассчитан на контентные сайты: content collections со схемой, связи между коллекциями, подсветка кода, компоненты-вставки, RSS;
- статику можно разместить где угодно.

Вся динамика выносится за пределы сайта или в изолированные острова: приём статей и согласование (ADR 0004, ADR 0008), уведомления и автопостинг (ADR 0004), в будущем — аккаунты читателей. Сайт забирает данные только во время сборки и в рантайме от сервисов не зависит.

### Детали реализации

1. Astro 6, только SSG, без SSR-адаптеров.
2. **Модель контента** (content collections со схемами на zod):
   - `rubrics` — рубрики, общие для всего контента;
   - `authors` — публичные профили авторов, в том числе гостевых: имя, подпись, фото, ссылки;
   - `articles` — статьи: заголовок, обложка (от дизайнера или сгенерированная), авторы (несколько, ссылки на `authors`), рубрика, дата, тело в Markdown;
   - `videos` — видео: эмбед из VK, Rutube или YouTube, описание, рубрика, дата;
   - `team` — участники команды для страницы «Команда».

   Страница рубрики показывает статьи и видео вместе по дате.
3. **Страницы MVP:** главная с описанием медийки, «Команда», «Контакты», рубрики, страницы статей и видео, страницы авторов.
4. Подсветка кода через Expressive Code. Кода в статьях будет немного (большие разборы уходят на стримы), так что продвинутые возможности не приоритет. Вставки описаны в ADR 0002.
5. **Интерактив:** обычный JS в `<script>` Astro-компонентов, спойлеры через нативный `<details>`. Общее состояние между островами — через **Nano Stores**.
6. **Закладки в MVP — без аккаунтов:** `@nanostores/persistent` хранит их в `localStorage` и синхронизирует между вкладками. Кнопка в статье, счётчик в шапке и страница «Мои закладки» читают один store.
7. **Подписки в MVP:** Telegram-канал и VK медийки (автопостинг, ADR 0004), RSS для всего сайта и для каждой рубрики (`@astrojs/rss`).
8. **Посетительская аналитика.** SITE-14 отложено без целевой версии. Редакция может принять и распространять MVP без счётчика. Гипотеза об аудитории и начало периода измерения определены в PRD §11.
9. SEO и превью ссылок: OG-картинки и мета-теги для каждой статьи и видео, потому что трафик идёт из пабликов.

### Аккаунты читателей (после редакции статей, версия 0.5)

Аккаунты не превращают сайт в SSR. Они делаются отдельным API в составе cms-api и интерактивным островом на статическом сайте. Вход — через VK ID и Telegram Login, имя и аватарка берутся у провайдера (ADR 0009). Закладки переносятся: при первом входе содержимое `localStorage` отправляется в API и сливается с серверными. Комментарии — после аккаунтов, отдельным решением.

## Альтернативы

* **Wagtail (Django CMS, монолит):**
  * *Плюсы:* полноценная админка, роли, согласование и отложенная публикация из коробки, StreamField. Стек Python, привычный для автора проекта. Есть LTS-релизы.
  * *Минусы:* нужны сервер, PostgreSQL, хранилище медиа, бэкапы и регулярные обновления. Без сопровождения проект деградирует, а после 2027 года сопровождать его некому. Для статьи раз в 1,5–2 недели возможности избыточны.

* **Headless Wagtail + фронтенд на Astro:**
  * *Плюсы:* максимальная гибкость, много бэкенд-работы.
  * *Минусы:* самая тяжёлая схема эксплуатации: два деплоя, CORS, авторизация API, превью черновиков через границу headless, ручная сериализация StreamField, пересборка по вебхукам или SSR. Требования проекта эту схему не оправдывают. По сути это Resume-Driven Development.

* **Astro + Git-based CMS (Keystatic, Decap, Sveltia):**
  * *Плюсы:* веб-админка поверх репозитория, отдельная БД не нужна.
  * *Минусы:* каждому автору нужен аккаунт на GitHub, нет согласования и отложенной публикации. Разобрано в ADR 0004.

* **SSR ради аккаунтов читателей:**
  * *Плюсы:* аккаунты, закладки и подписки делаются привычным серверным способом.
  * *Минусы:* весь сайт зависит от доступности сервера ради функции, которая не входит в минимум к запуску. Закладки в `localStorage` и подписки через паблики и RSS закрывают потребность на старте, а аккаунты позже добавляются островом без перехода на SSR.

## Последствия

### Положительные

* [+] Нет сервера под сайт: нечего ронять и обновлять, проект переживёт смену команды.
* [+] Дешёвый хостинг, перенос на другую площадку копированием папки.
* [+] Быстрая загрузка, хорошее SEO, на стороне сайта нет поверхности атаки.
* [+] Ошибки в контенте ловятся при сборке, а не у читателя.
* [+] Закладки работают без регистрации и без сервера.

### Отрицательные

* [-] Публикация требует пересборки и деплоя. Нужен CI.
* [-] Своего редакционного процесса нет, его приходится строить отдельно (ADR 0004, ADR 0008).
* [-] До появления аккаунтов закладки в `localStorage` привязаны к браузеру: на другом устройстве их не будет, а при очистке данных они пропадут.
* [-] Аккаунты, комментарии и другая пользовательская динамика возможны только через отдельный API и острова.
* [-] Команде нужен JS/TS-стек, а не только Python.
